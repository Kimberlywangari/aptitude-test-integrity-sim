# Before/after comparison and ablation

This is a preparation project on **simulated data**. The sittings, the honest timing and
the cheating behaviours were all generated by code in this repo, and the cheats are ones
I wrote myself. Nothing here describes real candidates, and nothing is auto-rejected: a
flag means "send to a human for review".

Every number below comes from the files in `results/`, which are written by the scripts
in `eval/`. The tables in this document are copied from `results/comparison_tables.md`,
which `python -m eval.make_tables` generates from those files.

## Summary

- On the same 2,501 simulated test sittings, the per-question detector flagged 297/376
  (79.0%) of the cheating sittings. The fixed-threshold baseline flagged 207/376 (55.1%).
  Fewer honest sittings were flagged too: 27/2125 (1.3%) against 35/2125 (1.6%).
- The whole net gain comes from one cheat type, `idle_burst`, which went from 3/113 (2.7%)
  to 113/113 (100.0%). The improved detector is **worse** on two other types:
  `too_fast` (112/113 (99.1%) down to 103/113 (91.2%)) and `uniform_timing`
  (35/75 (46.7%) down to 24/75 (32.0%)).
- In the ablation, the per-question timing rule on its own catches more than the fixed
  average-time rule on its own (239/376 (63.6%) against 151/376 (40.2%)), and it flags
  fewer honest sittings. The focus-loss rule catches a different group of cheats that
  neither timing rule sees.
- The gain depends on the z cutoff. At the cutoff I fixed in advance (1.5) it is large.
  At 1.0 the improved detector does worse than the baseline, and at 2.0 or 2.5 it finds
  almost nothing. This is a fragile result, not a robust one.
- The `idle_burst` result is 100% partly because I wrote that cheat to look like what
  this detector looks for. It says the code works as intended, not that it would find
  real cheating.

## 1. What changed and why

**Baseline (before).** Flag a sitting if its average time per question is below X
seconds, or its focus-loss events exceed Y. One global X is applied to every question.

**Improved (after).** Keep the focus-loss rule exactly as it was. Replace the average-time
rule with a per-question timing rule:

1. For each question, take the mean and standard deviation (population std) of seconds
   spent, using only the honest sittings in the reference half.
2. For each answer in a sitting, compute `z = (seconds - question mean) / question std`.
3. Count the answers with `z < -1.5` ("unusually fast for that question").
4. Flag the sitting if that count is at least K.

**Why.** An average hides things. A candidate who idles for a couple of minutes and then
clicks through the last 10 to 20 questions in a few seconds each can still have a normal
average, so a fixed average-time rule does not see them. A 20-second answer is also very
different on a question that normally takes 20 seconds and on one that normally takes 90.
Per-question baselines are the simplest way to take that into account.

**What is the same in both detectors.**

- The data, the reference/test split, and the test set (identical sittings for both).
- The focus-loss rule and its threshold (Y = 5).
- The false-alarm budget per rule. Every threshold (X, K, Y) is set from the honest
  reference sittings so that at most 1% of them trip that rule. No threshold is looked up
  from the test set.
- The detectors themselves never read the ground-truth columns (`tests/test_baseline.py`
  and `tests/test_improved.py` check this). The labels are used in two places only: to
  choose which reference sittings count as honest, and to score the flags.

**Setup.**

| Item | Value |
| --- | --- |
| Sittings | 5,000 simulated, 40 questions each, generator seed 42 |
| Cheats | 750 (15%): 225 `too_fast`, 225 `idle_burst`, 150 `focus_loss`, 150 `uniform_timing` |
| Split | 50/50 reference/test, stratified by cheat type, split seed 2024 |
| Learned from | 2,125 honest reference sittings (reference cheats are never used) |
| Scored on | 2,501 test sittings: 2,125 honest and 376 cheating |

## 2. Why these metrics

Flags go to a person, so there are two ways to be wrong, and each has a cost.

- **Recall** (cheats flagged / all cheats): how many cheats get to a reviewer at all.
- **False-positive rate on honest sittings** (honest flagged / all honest): how many
  honest candidates get pulled into review. This is the number the people affected by a
  wrong flag care about, so it is reported on honest sittings specifically.
- **Precision** (cheats flagged / all flagged): what share of the reviewer's queue is
  worth their time.
- **F1**: one summary of precision and recall. It weights them equally, which is a
  convenience and not a statement about their true costs, so I treat it as a sanity
  check and read the other columns.
- **Raw counts beside every percentage**, because several groups are small (75 sittings
  in the smallest) and a percentage alone hides that.
- **Per cheat type**, because the overall number hides the fact that one type got worse.

Plain accuracy would be misleading here: a detector that flags nobody would be right on
2,125 of 2,501 test sittings (85.0%).

Per-type rows are computed on all honest test sittings plus only that type's cheats.
Recall and false-positive rate mean what they say there. Per-type precision and F1 depend
on that smaller mix, so they should not be compared with the overall precision and F1.

## 3. Before/after results

Test set: 2501 sittings (2125 honest, 376 cheating). Thresholds learned from 2125 honest reference sittings.

| Improved | 324 | 297 | 27 | 79 | 2098 | 297/324 (91.7%) | 297/376 (79.0%) | 27/2125 (1.3%) | 594/700 (84.9%) |

### Table 5. Thresholds and reference false-alarm budget

| Setting | Baseline | Improved |
| --- | --- | --- |
| Timing rule | average seconds per question < 28.98 | at least 4 answers with z < -1.5 |
| Focus-loss rule | events > 5 | events > 5 |
| Honest reference sittings flagged by timing rule | 22/2125 (1.0%) | 11/2125 (0.5%) |
| Honest reference sittings flagged by focus-loss rule | 11/2125 (0.5%) | 11/2125 (0.5%) |
| Honest reference sittings flagged by either rule | 33/2125 (1.6%) | 22/2125 (1.0%) |

### What this shows

- **Overall the improved detector is better on this test set.** It caught 90 more
  cheating sittings (297 against 207) and flagged 8 fewer honest ones (27 against 35).
- **The gain is one cheat type.** `idle_burst` went from 3/113 (2.7%) to 113/113 (100.0%),
  a change of +110 sittings. The other three types net out to -20 (-9 on `too_fast`, +0 on
  `focus_loss`, -11 on `uniform_timing`), which is why the overall change is +90.
- **Two regressions.** `too_fast` went from 112/113 (99.1%) to 103/113 (91.2%) and
  `uniform_timing` from 35/75 (46.7%) to 24/75 (32.0%). The ablation below shows these
  types are caught better by the fixed average-time rule (Table 7), and that adding it
  back recovers them. My reading is that a sitting that is fast everywhere but not
  extreme on any single answer passes the "at least 4 answers beyond z = -1.5" test
  less often than it passes "average below 28.98 s". I did not measure that mechanism
  directly.
- **`focus_loss` is unchanged** at 57/75 (76.0%) because it is the identical rule, as it
  should be. This is a useful check that nothing else moved.
- **The lower false-positive count is partly a by-product of how K is chosen.** K must
  be a whole number. K = 3 would have exceeded the 1% budget, so K = 4 was used, and that
  leaves the improved timing rule using about half the budget on the reference sittings
  (11/2125 (0.5%) against 22/2125 (1.0%) for the baseline's timing rule, Table 5). So
  27 against 35 false positives is real on this test set, but it is not evidence that the
  method is intrinsically better at avoiding false alarms. I did not run a comparison at
  matched false-positive counts.

## 4. Ablation

Three rules are switched on and off, all on the same test set, all fitted from the same
reference sittings. **A** is the baseline's fixed average-time rule, **Z** is the
per-question z-score rule, **F** is the focus-loss rule. A variant flags a sitting if any
rule it contains fires. "A + F" is the baseline and "Z + F" is the improved detector; the
code checks that these two variants reproduce those detectors exactly
(`tests/test_ablation.py`).

### What the ablation shows

- **Each rule does a different job.** The per-question rule is the only one that sees
  `idle_burst` (113/113 (100.0%), against 3/113 (2.7%) for the average-time rule). The
  focus-loss rule is the only one that sees `focus_loss` (57/75 (76.0%), against 0/75
  (0.0%) and 1/75 (1.3%) for the timing rules). That follows from how I built the cheats,
  since each one disturbs only one signal, so treat it as a check that the code does what
  I intended and not as a finding about real cheating.
- **The per-question timing rule beats the fixed average-time rule on its own**:
  239/376 (63.6%) at 10 false positives, against 151/376 (40.2%) at 18. That is the
  clearest evidence for the technique in this project, again on cheats I injected.
- **The regressions come from dropping the average-time rule.** Putting it back
  (A + Z + F) catches 113/113 (100.0%) of `too_fast` and keeps 35/75 (46.7%) of
  `uniform_timing`, for 318/376 (84.6%) recall overall. That variant also flags more
  honest sittings than any other (37/2125 (1.7%)). It was not the improved detector I set
  out to test, so it is reported here as an observation and not as the headline.
- **Removing a rule from A + Z + F costs:** 111 cheats if Z is removed (318 to 207),
  56 if F is removed (318 to 262), and 21 if A is removed (318 to 297).

### What the sensitivity table shows

- **The cutoff of 1.5 was fixed in the code before any improved-detector result existed**
  (it was added in the commit that introduced the detector, and the results were
  recorded two commits later). It was not tuned on the test set. But it is the best of the
  four values tried, and the neighbours are much worse, so the headline should be read as
  "the best setting in a small grid", not as a stable estimate.
- **At 1.0** the rule needs K = 27 of 40 answers to stay inside the false-alarm budget,
  which turns it into an average-speed rule. It then catches 194/376 (51.6%), below the
  baseline's 207/376 (55.1%) at the same 35 false positives, and it misses `idle_burst`
  again (3/113 (2.7%)).
- **At 2.0 and 2.5** almost nothing fires beyond the focus-loss rule. This is a limit of
  z-scoring raw seconds. Times cannot go below the 2 s floor and each question's standard
  deviation is about half its mean (0.48 to 0.56 of it, in `improved_thresholds.json`),
  so a z-score cannot get very negative. From the saved per-question stats, the lowest z
  any answer can reach is between -2.04 and -1.68
  (median -1.89). A cutoff of -1.5 is reachable on 40 of 40 questions, -2.0 on 7 of 40,
  and -2.5 on 0 of 40, so at 2.5 the rule cannot fire at all. (These figures are the
  last section of `results/comparison_tables.md`.)
- I did not try a transformed scale (for example z-scores of log-seconds), which is the
  obvious way to address this. That is not built.

## 5. Limitations and unexpected outcomes

- **Everything is simulated, and the cheats are mine.** The detector's best result
  (`idle_burst`, 100%) is on a cheat I defined as 10 to 20 final answers at 3 to 8
  seconds after an idle gap, which is exactly the pattern a per-question z-score is
  built to see. The result confirms the code works. It is not evidence of real-world
  performance.
- **Honest behaviour is guessed.** Pace, per-answer wobble, interruptions and end-of-test
  rushing are my own plausible-looking distributions. Real candidates will differ, and
  honest-but-fast candidates are the main false-positive risk in practice.
- **Each cheat disturbs one signal only.** Real cheating mixes signals (a lookup session
  would likely show focus loss and unusual timing together), which would probably make
  detection easier, but I did not simulate that.
- **Two regressions** (`too_fast`, `uniform_timing`) were not expected going in. On the
  strength of Table 7, the per-question rule looks better used alongside the average-time
  rule than as a replacement for it. I only tested that combination (A + Z + F) after
  seeing the results, so it is an observation to confirm, not a result I planned for.
- **`uniform_timing` is weak for both detectors** (35/75 (46.7%) and 24/75 (32.0%)). The
  ones that are caught are caught because the constant pace happens to be fast, not
  because it is uniform. Neither detector looks at how much a sitting's timing varies.
  A spread feature is the obvious next step and is not built.
- **One seed, one run.** I did not repeat the experiment over several generator seeds
  and have no confidence intervals, so I cannot say how stable the 55.1% to 79.0% gap is.
- **K and the question stats are fitted on the same reference sittings**, so the
  reference false-alarm figures in Table 5 are slightly optimistic. The test-set
  false-positive counts are the clean numbers.
- **The reference is assumed clean.** I used the ground-truth labels to pick the honest
  reference sittings. A real reference would be unlabelled and might contain cheats,
  which would pull the per-question baselines. That is not simulated.
- **Per-type precision and F1** depend on the smaller honest-plus-one-type mix (see
  section 2).

## 6. Reproduce

From the repo root (Python 3.14.7; versions in `requirements.txt`):

```
pip install -r requirements.txt
python -m pytest -q
python -m src.make_data
python -m eval.run_baseline
python -m eval.run_improved
python -m eval.run_ablation
python -m eval.make_tables
```

`eval.run_improved` expects `results/baseline_metrics.csv` to exist (it checks that its
recomputed baseline counts match it), so run the baseline first. Files written, and the
tables they feed:

| Script | Writes | Used for |
| --- | --- | --- |
| `eval.run_baseline` | `results/baseline_metrics.csv`, `results/baseline_thresholds.json` | Baseline rows, Table 5 |
| `eval.run_improved` | `results/improved_metrics.csv`, `results/improved_thresholds.json`, `results/before_after.csv` | Tables 1 to 5 |
| `eval.run_ablation` | `results/ablation_metrics.csv`, `results/z_threshold_sensitivity.csv` | Tables 6 to 8 |
| `eval.make_tables` | `results/comparison_tables.md` | The tables in this document |
